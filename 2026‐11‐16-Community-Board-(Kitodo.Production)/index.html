    TOP 1 Automatische Strukturierung in Kitodo.Production mit der Hilfe von LLMs

    • siehe Notizen aus der letzten Sitzung
    • Fortschritte bei Christoph Bartmann und Kerstin Wendt
    • Christoph hatte dies in Mannheim auf dem Kitodo-Praxistreffen für einen alten Druck vorgestellt
    • Kerstin hat mit „Drucksachen der Bürgerschaft“ (200.000 Seiten) experimentiert
      • Das Vorgehen mit der Vorlage von Christoph und mehreren Änderungen war nicht erfolgreich.
      • Der Schlüssel war ein Artikel von Daniel van Strien. Danach wurde mit korrekten Vorbildern (Bilddateien mit Erklärung) angelernt. Anschließend konnte Claude die Sachen (bis auf wenige Ausnahmen, wo auch das Fehlen einer Vorlage gemeldet wurde) sehr gut verarbeiten.

    Mit welchen freien/lokalen Modellen kann gearbeitet werden. Christoph hatte gute Ergebnisse mit Qwen.

    Offene Fragen: - welche sind gute Ausgabeformate? - bisher wurde mit flachem JSON gearbeitet, das die Strukturhierarchie und Metadaten enthält. - Wie können aus Kitodo heraus Prompts erstellt werden? - Wird zunächst zurückgestellt - Wird eine Verarbeitung in Batches durch Kitodo verwaltet? - Wie werden Ergebnisse gegen das Ruleset validiert? - Wie lässt sich die Zeit, die das Generieren von Strukturdaten benötigt stark verringern?

    Austauschformate - Als Gesamtergebnis oder pro Bild - Ggf. noch einmal durch LLM konvertiert - Grundsätzlich sollte der Umgang von Kitodo mit den resultiernden Dateien möglichst analog zum Vorgehen bei der OCR sein - Die technische Umsetzung ginge auf Basis einer klar vorgegebene Ordnerstruktur - Ein Vorschlag wird nach der Analyse abgelegt und dann per Kitodo angenommen oder verworfen - Christoph hat implementiert, dass die Funktion zum Schreiben von XML aus dem Metadateneditor zum Speichern im XML verwendet, wodurch die Daten im Metadateneditor sichtbar und durch die Suche auffindbar sind. - derzeitiges JSON enthält drei Elemente zur Beschreibung von Strukturdaten: - page -> Image-Nummer - Beispiel: 00000011 - type -> Bezeichnung Strukturelement-Typ - Beispiel: chapter - label -> Metadatum des Strukturelment - Beispiel: DISPUTATIO I. De materiali objecto Pœnitentiæ. - Klicken auf Details für Beispiel JSON

  {
    "page": "00000003",
    "type": "title",
    "label": "CURSUS THEOLOGICUS P. DOMINICI VIVA SOCIETATIS JESU. PARS OCTAVA DE POENITENTIA UT VIRTUTE, ET UT SACRAMENTO."
  },
  {
    "page": "00000005",
    "type": "other",

  },
  {
    "page": "00000009",
    "type": "index",
    "label": "INDEX QUÆSTIONUM De Pœnitentia ut Virtute, & ut Sacramento."

  {
    "page": "00000011",
    "type": "part",
    "label": "PARS OCTAVA DE POENITENTIA UT VIRTUTE, ET UT SACRAMENTO."
  }
]
    • Zu entscheiden: welches Element soll für die Übertragung der Metadaten verwendet werden? LABEL? TITLE?
    • LABEL ist naheliegend, kann beim Exportieren umgewandelt werden.
    • Generell soll die Umsetzung zunächst so einfach wie möglich sein
    • In der JSON-Datei wird derzeit nur label angewendet; Perspektivisch könnte auch metadata hinzugefügt werden
      • In Kitodo.Production wäre eine Konfigurationsmöglichkeit sinnvoll, um Titelinformationen in das jeweils am häufigsten Metadatum einzutragen
      • Köln: LABEL
      • SLUB/SUB: TitelDocMain
    • Keine Abbildung von Struktur-Hierarchien
    • Keine Berücksichtigung von Metadatengruppen

    Für die Zusammenführung und Spezifizierung der Anforderungen wird eine GitHub-Diskussion erstellt.

    TOP 2 Ausbau von überholten Features - Zeitungen (Untypisierte Elemente)

    • Siehe: https://github.com/kitodo/kitodo-production/wiki/Liste-der-Funktionen-mit-unklarer-Anwendung

    • Hauptziele (Einführung neuer Funktionen)

    • Umsetzung des Anlegens von Vorgängen für einzelne Ausgaben ohne untypisierte Elemente für Monat und Tag.
    • Anpassung Export:
      • Erstellung der benötigten <mets:div> für Monat und Tag in die METS-Datei der Ausgabe
      • Ermittlung den Datum-Werte aus der Jahresdatei (via Kitodo-ID des Vorgangs) und Eintrag in die erstellten <mets:div>
    • Kitodo.Production muss zunächst beide Varianten verarbeiten können
    • Dadurch besteht kein Druck bezüglich Anpassung der Altdaten
    • Dadurch muss die Funktion für die Granularität/Vorgangsaggregierung nicht ausgebaut werden
    • Umgang mit bestehender Funktion Granularität/Vorgangsaggregierung
    • Das Interface für die Erstellung der Granularität/Vorgangsaggregierung wird zunächst nur ausgeblendet, nicht ausgebaut
    • Es kann nicht zuverlässig ermittelt werden, ob die Funktion benötigt wird - durch eine Deaktivierung der Funktion kann geprüft werden, ob das Fehlen Beunruhigung auslöst.
    • Dadurch kann die Bearbeitung der Hauptziele konzentriert werden
    • Migration/Korrektur der bestehenden Vorgänge
    • Dies kann erst später erfolgen

    • Bezieht sich nur auf das Entfernen der untypisierte Elemente in den Vorgängen der Ausgaben

    • Weiteres Vorgehen

    • Organisation Treffen einer Kleingruppe. Unter Umständen im nächsten Treffen des Kitodo.Community Board
